# Q 表蒸餾式 DQN：設計心法

---

## 一、萬變不離其宗：RL 的本質

不管 Q-Learning、DQN、Actor-Critic、PPO……
所有強化學習算法的核心都是同一件事：

> **從 SAR 循環中累積經驗，調整策略。**

State → Action → Reward → 下一個 State → 下一個 Action → …

這個循環不會因為換了算法而改變。
改變的只是：**經驗被如何記憶、如何調用。**

---

## 二、Q-Table 與 DQN 的真正差異

傳統的說法是「DQN 用神經網路取代 Q-Table」，
但這個說法遮蔽了更重要的事：

| | Q-Table | DQN |
|---|---|---|
| 記憶形式 | 點對點查表 | 函數逼近 |
| 沒見過的狀態 | 傻掉（返回初始值） | 內插/近似 |
| 可解釋性 | 高（直接看表格） | 低（黑盒） |
| 樣本效率 | 每筆資料直接寫入 | 需大量樣本訓練 |
| 穩定性 | 高 | 訓練不穩定 |

**Q-Table 的問題不是「錯了」，而是「不會舉一反三」。**
DQN 解決的也不是學習原理，而是記憶的泛化能力。

---

## 三、為什麼不直接用標準 DQN

標準 DQN 的訓練流程是：
1. Agent 與環境互動，收集 `(s, a, r, s')` 存入 replay buffer
2. 從 buffer 隨機取樣，對神經網路做 Bellman 更新
3. 用 target network 穩定訓練目標

這個做法的問題：
- 訓練早期 reward 稀疏，神經網路訓練信號雜訊大
- 需要 replay buffer、target network 等工程技巧
- 對初學者來說像黑盒，難以直觀理解
- Q-Table 的可解釋性完全丟掉了

### 實際踩到的坑：訓練資料分布偏斜

早期實作用的是傳統做法：把近期 1000 步的 `(s, a, r, s')` 存成 replay buffer，定期取批次訓練。

但 RL 在玩遊戲的過程中，Agent 很容易卡在狀態空間的某個小角落——
例如 CartPole 在學會之前，桿子幾乎都在傾倒過程中，
狀態資料集中在「快死掉」那一帶，覆蓋範圍極小。

結果：神經網路在局部區域 overfitting，對其他大多數狀態一無所知，訓練效果很差。

這是標準 DQN 在 replay buffer 設計上會花大量工夫的原因（prioritized replay、均勻採樣等），
但本質上是在用工程手段彌補「訓練資料分布不均」的問題。

### 轉折：Q-Table 的 bucket 中心是天然均勻的訓練資料集

Q-Table 的每個格子，對應狀態空間中的一塊區域，格子的中心點是那塊區域的代表值。
只要 Q-Table 有 N 個格子，就有 N 筆均勻覆蓋整個狀態空間的訓練資料——
**不管 Agent 實際走過哪裡，訓練資料的覆蓋率都是一樣的。**

原本期待 DQN 自己訓練出來的 Q 值曲線，
能不約而同地跟 Q-Table 長得相似——結果當然不會。

後來轉念：**既然目標本來就是逼近 Q-Table，那直接把 Q-Table 當訓練標籤去 fit，不就解決了？**

與其期待神經網路自己摸索出跟 Q-Table 一樣的形狀，
不如直接告訴它答案，讓它學會「在任意連續狀態下，複現 Q-Table 的判斷」。

這種做法在機器學習領域有正式的名稱：**知識蒸餾（Knowledge Distillation）** 或 **模仿學習（Imitation Learning）**——
讓一個較靈活的模型（學生）去學習一個較穩定的來源（老師）的輸出，而不是直接從原始資料學起。

## 四、設計靈感：演員—評論家（Actor-Critic）

Actor-Critic 的核心精神：

> **不是讓一個系統獨力完成所有工作，
> 而是讓「穩定的評估者」輔助「泛化的行動者」。**

- **Critic（評論家）**：給出穩定的價值評估，作為訓練信號
- **Actor（演員）**：從 Critic 的評估中學習，負責做決策

這個分工的好處是：Actor 不用直接面對環境的雜訊，
他的老師（Critic）已經把複雜的信號整理成清晰的指導。

---

## 五、Qt + 網路的設計哲學

把 Actor-Critic 的精神，映射到 Q-Table 與神經網路上：

> **Q-Table 退居幕後，扮演 Critic 的角色。
> 神經網路在前台，扮演 Actor 的角色。**

兩個系統**從遊戲開始就同時運行**，不是「先學 Q-Table 再換 DQN」：

```
         環境（SAR 循環，持續不斷）
              ↓ 實際 reward
┌─────────────────────────────┐
│  Q-Table（每步即時更新）      │ ←─── Q-Table 模式：用自己的 max Q(s') 做 Bellman 更新
│  離散記憶、點對點、可解釋     │ ←─── DQN   模式：改用 DQN 的 max Q(s') 做 Bellman 更新
└────────────┬────────────────┘
             │ 定期蒸餾（知識蒸餾，DQN 向 Q-Table 學）
             ↓
┌─────────────────────────────┐
│  DQN 神經網路                │
│  fit 逼近 Q-Table 的形狀     │
└────────────┬────────────────┘
             │ 提供泛化的 max Q(s') 回饋給 Q-Table
             └──────────────────────────────────────┘
```

**這是雙向互學，不是單向蒸餾：**

- **「年輕人跟前輩學」**：DQN 持續 fit 逼近 Q-Table，繼承它累積的真實經驗
- **「前輩也跟上年輕人」**：Q-Table 在 DQN 模式下，Bellman 更新的 `max Q(s')` 改從 DQN 拿——DQN 已泛化整個狀態空間，連 Q-Table 從未走到的 s' 也能給出估計值，Q-Table 的學習速度因此大幅加快

**UI 切換「Q-Table / DQN 模式」實際控制的是三件事：**

| 切換項目 | Q-Table 模式 | DQN 模式 |
|----------|-------------|---------|
| 動作選擇 | Q-Table 查表 | DQN predict |
| 熱力圖顯示 | Q-Table 的稀疏格值 | DQN 對整個狀態空間的連續預測 |
| Q-Table Bellman 更新的 max Q(s') 來源 | Q-Table 自己 | DQN 的泛化估計 |

第三點是加速效果的關鍵：DQN 的泛化能力反過來讓 Q-Table 的每一步更新都更有資訊量。

## 六、為什麼這樣做更合理

### 穩定性
Q-Table 經過足夠多的 episode 之後，已探索格子的 Q 值趨於穩定。
用穩定的 Q-Table 當訓練目標，比用即時的 Bellman 殘差更不容易震盪。

### 可解釋性保留
Q-Table 的熱力圖、覆蓋率分析、動作分布等可視化工具全部保留。
學習者可以同時觀察：「Q-Table 學到了什麼」和「神經網路怎麼繼承它」。

### 演進的可觀察性

熱力圖永遠顯示 Q-Table 的內容——但在 DQN 模式開啟後，它顯示的不再只是 Q-Table 自己的經驗。

- **Q-Table 模式**：有值的格子一定是 Agent 走過的，圖案像路徑、像連通區域
- **DQN 模式**：偶爾出現孤立的格子突然有值，周圍全是空白

那些孤立的點，是 Q-Table 在 Bellman 更新時借用了 DQN 的估值——
DQN 替 Q-Table「想像」了它從未走到的狀態應該有多少價值，
Q-Table 把這個想像寫進了自己的記憶。

> 「明明周圍沒有獎勵，怎麼突然就有估值，而且還有用——
> 這就是表格前輩在吸取年輕人舉一反三的小聰明。」

熱力圖因此變成了雙向互學的觀測窗：
不需要另外畫 DQN 的圖，Q-Table 的圖本身就記錄了 DQN 影響它的痕跡。

### 經驗檔格式統一

標準 DQN 若要儲存已學到的知識，需要序列化神經網路權重（TensorFlow SavedModel、ONNX 等），
跨版本、跨框架都可能遇到相容問題，對初學者來說幾乎是黑盒。

蒸餾式 DQN 的知識源頭始終是 Q-Table，因此：

> **匯出的 JSON 對 Q-Table 模式與 DQN 模式完全共用。**

- Q-Table 模式練出的經驗，可以直接載入後切換 DQN 模式繼續——
  Worker 立即蒸餾，不需要額外轉換
- 使用者不需要理解神經網路序列化，「存檔」和「載入」的行為對他們始終透明一致
- Q-Table JSON 本身就是人類可讀的格式，可以手動檢視、比較、分享

**這不是刻意設計出來的功能，而是「Q-Table 作為知識中介層」這個架構決策的自然結果。**

### 教育意義
這個設計本身就在示範一個重要觀念：
> **新方法不一定要完全推翻舊方法，
> 舊方法的穩定性反而可以成為新方法的基礎。**

## 六之一、常見質疑：維度爆炸問題

這種做法常被質疑：**Q-Table 的格子數隨狀態維度指數成長，資料量爆炸，根本不實際。**

這個質疑預設了「Q-Table 的訓練資料 = 整個狀態空間的所有格子」。
但實際情況並非如此。

### 真正的訓練資料：已探索且有效的格子

神經網路的訓練對象，只有 Q-Table 中：
- **已被 Agent 走訪過**（曾有 SAR 經驗流過）
- **動作評估值有意義**（非初始值 0，有實際更新過）

的那些格子。

RR 平台的分析頁面有即時計算這個比率（已探索格數 / 總格數）。
實際觀察下來，**即使訓練很長時間，覆蓋率通常仍極低**——
大量邊際極端狀態從未被探索過，那些格子當然也不需要被神經網路學到。

### 戰爭迷霧的比喻

這就像遊戲裡常見的**戰爭迷霧（Fog of War）**：

> 地圖很大，但 Agent 真正走過、有情報的區域是有限的。
> 神經網路只需要學習「已點亮的區域」，而不是整張地圖。

未探索的狀態，對當前任務來說本來就不重要；
若未來 Agent 真的走到那裡，Q-Table 會繼續更新，神經網路也會在下一輪 fit 中補上。

### 小結

| 假設 | 實際 |
|------|------|
| 訓練資料 = 全部格子（指數爆炸） | 訓練資料 = 已探索且有效的格子（遠小於理論上限） |
| 狀態空間維度高 → 不可行 | 覆蓋率低 → 訓練集小且集中 → 反而更好訓練 |

**維度爆炸的問題在「理論格子數」，不在「有效訓練資料量」。**

## 七、為什麼用 Web Worker 包裝 DQN

### 兩種「學習」的時間尺度完全不同

| | Q-Learning | DQN fit |
|---|---|---|
| 觸發時機 | 每一步 action 後 | 定期批次 |
| 計算量 | 極輕（一次查表更新） | 重（批次梯度下降、多 epoch） |
| 時間尺度 | 毫秒級 | 數百毫秒～秒級 |
| 能否阻塞主執行緒 | 不能 | 絕對不行 |

Q-Learning 必須跟著 game loop 跑，每收到一個 `reward_state` 就立刻更新，延遲不能高。
DQN fit 則是重計算——用整批 Q-Table 資料做梯度下降，如果放在主執行緒，直接卡死 UI 和遊戲。

### Web Worker 的角色

Web Worker 在獨立的執行緒中運行，解決了這個衝突：

```
主執行緒（game loop）
  └─ Q-Learning：每步更新 Q-Table（輕量、即時）
  └─ 定期把 Q-Table 變動同步給 Worker
  └─ 需要推論時：postMessage → Worker → 等回應

Worker 執行緒
  └─ 持有 Q-Table 的副本
  └─ 持續執行 DQNfitToQTable()（重計算、非同步）
  └─ 收到 predict 請求 → 回傳 Q 值
```

兩個執行緒各跑各的，Q-Learning 不等 DQN，DQN 也不卡 Q-Learning。
Worker 的工作就是「一直追上最新的 Q-Table 狀態」——就算追不上，也不影響遊戲運行。

### Worker 的代價

Web Worker 與主執行緒之間只能透過 `postMessage` 通訊，
等於要在遊戲的 postMessage 協定之外，再維護一套 Worker 內部的訊息協定。

這也是實作卡住的原因之一——腦袋裡同時有兩層 postMessage 在轉。

## 九、技術對應

| 概念 | Actor-Critic | 本設計 |
|------|-------------|--------|
| 穩定的評估者 | Critic（價值網路） | Q-Table |
| 泛化的決策者 | Actor（策略網路） | DQN |
| 訓練信號來源 | Critic 的 TD 誤差 | Q-Table 的 Q 值 |
| 泛化機制 | 策略梯度 | 監督式擬合（MSE） |
