# Blockly 對於 RR 的設計演進與存在必要性

---

## 被捨棄的用法

最初構想用 Blockly 讓學生「用積木寫 Q-learning 算法」。

實際評估後直接捨棄——太複雜，對學生沒有意義。
學生只需要 slider 調超參數、看 Agent 反應就好，不需要自己寫算法邏輯。

---

## 找到定位的四個使用場景

### 1. 自訂狀態前處理

通用的池化 / 正規化在某些環境不夠用。

例如有物理模擬的遊戲，可以透過計算相對座標進行狀態降維：
兩物的絕對座標 → 相對座標，減少 state space，加速 Agent 學習。

這類環境特有的數學轉換無法標準化，適合用 Blockly 讓學生或開發者自己定義，而非硬編碼進平台。

### 2. Bootstrap 腳本（策略助推器）

複雜環境讓 Agent 從 0 開始隨機探索太慢，
尤其是 policy-based 算法（一回合才結算），等到累積足夠經驗要搞到天荒地老。

解法：先由人類用 Blockly 寫一個簡單的規則腳本作為初始策略（先求有再求好），
讓 Agent 從「有一點方向」的地方開始學，而不是從純隨機出發。

### 3. 訓練完備的 DQN 逆推成可讀判斷式

訓練完的 DQN 本質上是一個複雜的公式解。
可以逆推成一系列數值判斷條件，讓人類讀得懂。

用 Blockly 重現這個判斷邏輯，讓學生看到「模型學到的規則長什麼樣子」，
把黑盒的神經網路決策變成可讀的積木結構。

### 4. 人類腳本 vs RL Agent 對決

讓學生自己用 Blockly 寫策略腳本，和訓練好的 RL Agent 競爭。

直觀感受「寫死的規則」與「從經驗學習的策略」有何本質差異——
這也是讓學生搞清楚「何謂腳本、何謂 RL」最直接的方式。

---

## 核心定位

RR 的 Blockly 是在**創造邏輯**：寫 policy 腳本，決定 Agent 如何行動。

> 對比：DD 的 Blockly 是**記錄與組織行為**——巨集，不是程式。
> 兩者用的是同一個工具，但扮演完全不同的角色。
