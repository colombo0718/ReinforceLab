# 錄放系統開發計畫

> 建立日期：2026-05-02
> 狀態：計畫中

---

## 一、定位與目標

錄放系統是 RR 平台的基礎建設，不是功能噱頭。

**它解決的核心問題：**
- 現在 Agent 訓練的過程是一次性的——學了就學了，沒有記憶、沒有存檔、無法回溯
- 研究者（colombo）、觀測腳本（Playwright）、未來的 AI 分析員都沒有「對局歷程」可讀
- 沒有歷程資料，就沒有辦法做 Imitation Learning、Offline RL、或 LLM 分析打法

---

## 二、雙軌架構

從 2026-05-01 會議提煉出的核心設計原則：

**人生軌跡（外軌）** = 行為事件序列 → 對應 RL 的 SARS 軌跡

**心路歷程（內軌）** = 認知狀態變化 → 對應 Q-table 演化

兩條時間線獨立紀錄，用事件 ID 關聯。

```
外軌（episode trajectory）：
  [ { t, s, a, r, s', done }, { t, s, a, r, s', done }, ... ]

內軌（value evolution）：
  [ { tau, trigger_t, delta_Q, affected_states }, ... ]

關聯表：
  trigger_t=3 → tau=1（t=3 的那一步觸發了第一次認知更新）
```

## 三、資料格式規格

### 3.1 外軌：單步紀錄

```js
{
  t: 42,              // 步數（episode 內）
  s: [0.3, 0.7, 2],  // state（原始值，未 bucket 化）
  a: 1,              // action index
  r: -1.0,           // reward（本步）
  s_next: [0.4, 0.6, 2],
  done: false,
  ticks: 3           // 即時制遊戲用；回合制填 1
}
```

### 3.2 外軌：episode 元資料

```js
{
  ep: 47,
  game: "fighter",
  algo: "qtable",
  params: { alpha: 0.3, gamma: 0.95, epsilon: 0.1 },
  total_reward: 28.5,
  steps: 312,
  ts_start: 1746000000000,  // Unix ms
  ts_end:   1746000012345,
  trajectory: [ ...步資料陣列... ]
}
```

### 3.3 內軌：Q-table 快照事件

```js
{
  tau: 1,
  trigger_t: 42,           // 觸發這次更新的外軌步數
  trigger: "td_error",     // 觸發類型：td_error / episode_end / manual
  td_error: -3.7,          // TD error 幅度（大 = 意外大）
  affected_state: [3, 7],  // bucket index（受影響的格子）
  delta_Q: {
    "3,7": { a0: -0.4, a1: 0.0, a2: 1.2 }  // 各動作 Q 值變化量
  }
}
```

> **快照頻率策略：** 不是每步都記，只記 `|TD error| > threshold` 的更新，避免資料爆炸。
> threshold 建議：max Q range 的 5%，可設為參數。

### 3.4 檔案格式

```
experiments/
  fighter-ep047-20260502T103012.json   ← 單集完整紀錄
  session-20260502-fighter.jsonl       ← 多集串流（JSONL，一行一集元資料）
```

JSONL 格式讓 Playwright / Agent 腳本可以 tail -f 方式讀取，不需要等整個訓練結束。

## 四、施工計畫

### Phase 1：外軌收集（Episode Recorder）

**目標：** 每集自動儲存 SARS 軌跡到 `window.rrEpisodeBuffer`，集結束後可存檔

**改動位置：** `index.html` 的 `reward_state` 處理區塊

```js
// 每步收到 reward_state 時
window.rrEpisodeBuffer.push({
  t: stepCount,
  s: lastState,
  a: lastAction,
  r: msg.reward,
  s_next: msg.state,
  done: msg.done,
  ticks: msg.ticks ?? 1
});

// done: true 時
const episode = {
  ep: episodeCount,
  game: currentGame,
  algo: currentAlgo,
  params: { alpha, gamma, epsilon },
  total_reward: episodeReward,
  steps: window.rrEpisodeBuffer.length,
  ts_start: episodeStartTime,
  ts_end: Date.now(),
  trajectory: window.rrEpisodeBuffer
};
window.rrSessionLog.push(episode);
window.rrEpisodeBuffer = [];
```

**UI：** Tab 列加回 `📽️錄放`（`p1-replay`），顯示：
- 目前 session 的集數與總步數
- 按集數/得分排序的 episode 列表
- 選取某集 → 回放（重送 action，不學習）
- 導出按鈕（下載 JSON / JSONL）

---

### Phase 2：內軌收集（Value Evolution）

**目標：** 在 `reinforceEngine.js` 的 `updateQ()` 中記錄 TD error 超過 threshold 的更新

**改動位置：** `reinforceEngine.js`

```js
// updateQ() 更新後
const tdError = r + gamma * maxNextQ - oldQ;
if (Math.abs(tdError) > Q_SNAPSHOT_THRESHOLD) {
  window.rrValueLog.push({
    tau: window.rrValueLog.length,
    trigger_t: window.rrStepCount,
    trigger: "td_error",
    td_error: tdError,
    affected_state: stateKey,
    delta_Q: { [stateKey]: { [action]: newQ - oldQ } }
  });
}
```

**關聯：** episode 元資料加 `value_events: [tau indices]`，讓 AI 分析時知道「這集哪幾步有顯著認知更新」。

---

### Phase 3：回放機制

**目標：** 選取任意已錄 episode，RR 以「只送 action、不更新 Q-table」模式重播

核心邏輯：
1. 把 episode.trajectory 的步資料排成隊列
2. 每次收到 `reward_state` 時從隊列取下一步的 `a`，直接送出（不走 Q-table 決策）
3. `isPaused` / `accel` 照常運作
4. 回放模式下圖表仍更新（可觀察重播時的 reward 曲線）

---

### Phase 4：AI 分析介面（長期）

**目標：** Playwright 腳本或 LLM Agent 可讀取 `experiments/` 下的對局歷程，進行分析

```js
// 暴露給外部腳本的介面（延伸現有 rrLog）
window.rrSessionLog        // 完整 session（含 trajectory）
window.rrSessionSnapshot() // 深拷貝
window.rrValueLog          // 內軌快照序列
```

Playwright 腳本可以：
```python
session = page.evaluate("window.rrSessionSnapshot()")
# 挑最高分的 5 集
top5 = sorted(session, key=lambda e: e['total_reward'], reverse=True)[:5]
```

LLM 分析流程（概念）：
```
讀 session_log → 抽高分集 trajectory → 找 high TD error 時刻
→ 對照 state / action / reward → 輸出文字分析 or Blockly 積木腳本
```

## 五、與現有架構的對接

| 現有機制 | 錄放系統如何用 |
|---------|--------------|
| `window.rrLog` | 繼續維護（相容 Playwright），錄放系統是它的超集 |
| `window.rrStepCount` | 作為外軌的 `t` 欄位 |
| `reinforceEngine.js updateQ()` | 在這裡 hook 內軌快照 |
| `experiments/` 資料夾 | 匯出 JSON/JSONL 的存放位置 |
| postMessage 協定 | 不動，`ticks` 欄位已支援 |

---

## 六、開發順序建議

```
Phase 1（外軌收集 + 基本 UI）     ← 先做，收益最高
Phase 2（內軌收集）               ← Phase 1 完成後接著做
Phase 3（回放機制）               ← 需要 Phase 1 的 buffer
Phase 4（AI 分析）                ← 長期，依需求推進
```

Phase 1 + 2 完成後，`experiments/` 資料夾就有意義了，AI 觀測 RL 訓練的基礎建設就算打通。

---

## 七、注意事項

- 軌跡資料量估算：每步 ~200 bytes，1000 步的集 = 200KB，100 集 = 20MB。瀏覽器 `window` 放太多集會有記憶體壓力，建議 session 內只保留最近 N 集（預設 50），舊的自動滾出。
- 回放模式下禁止 Q-table 更新（加 `isReplaying` flag，在 `updateQ` 入口 early return）
- 導出格式選 JSONL 而非單一大 JSON，方便 Python 逐行讀取
